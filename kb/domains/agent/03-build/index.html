    03-build

    Step 1：问题闭环与能力边界定义

    • 输入输出定义（I/O Schema Design）
      明确系统接收的数据结构与最终输出形式（结构化结果或具体动作），避免“只回答不执行”的模糊交付。

    • 任务成功标准与失败定义（Success & Failure Criteria）
      设定可量化的完成标准（如正确率、完成率），并定义异常、缺信息、低置信度等失败场景的处理策略。

    • 读写权限与操作边界（Read/Write Scope Control）
      区分查询类操作与有副作用的写操作，限制高风险行为（如支付、删除、通知）必须经过确认或人工介入。

    Step 2：设计核心数据与状态流转

    • 任务数据结构定义（Task Schema）
      统一任务对象的数据结构，承载输入、上下文、状态与执行结果，避免依赖模型隐式记忆。

    • 工作流/状态机设计（Workflow / State Machine）
      将任务拆解为明确阶段（如解析→校验→执行→收敛），定义状态流转路径与执行顺序。

    • 关键流程去LLM化（Deterministic Control over LLM）
      将关键决策逻辑（如状态迁移、权限判断）由代码控制，LLM仅负责理解与辅助判断。

    Step 3：LLM选型与提示词工程

    • LLM选型（Model Selection）
      根据任务复杂度与成本选择合适模型，区分轻量理解任务与复杂推理任务。

    • Prompt结构规范（Prompt Schema Design）
      定义统一的输入输出格式（如JSON schema），确保结果可解析、可校验、可接入系统。

    • Prompt单一职责与稳定性（Single-responsibility Prompt Design）
      每个prompt只解决一个问题，并通过约束与示例提升输出一致性与稳定性。

    Step 4：构建标准化工具库（Tools & Skills）

    • 工具接口标准化（Tool API Schema）
      统一工具的参数、返回结构与描述方式，确保LLM能够正确理解与调用。

    • 工具异常处理与容错机制（Retry / Timeout / Fallback）
      封装超时、失败与异常情况，提供重试与降级策略，提升系统稳定性。

    • 工具副作用分级与权限控制（Side-effect & Permission Control）
      区分只读与写操作，对高风险行为增加权限限制与人工确认机制。

    Step 5：搭建记忆与推理机制

    • 短期记忆与长期记忆设计（Memory Architecture）
      管理当前任务上下文与可复用历史信息，提升多轮交互一致性与效率。

    • 推理-行动循环设计（Reasoning-Action Loop）
      构建“理解→决策→调用工具→再判断”的循环流程，而非一次性生成结果。

    • 结果校验与执行回退机制（Validation & Retry / Rollback）
      对执行结果进行校验，在异常或错误路径中支持回退与重试。

    Step 6：建立可观测性与调试链路

    • 全链路日志与执行轨迹（Tracing & Logging）
      记录输入、模型输出、工具调用与状态变化，形成完整执行链路。

    • 任务复现与回放机制（Replay System）
      保存任务运行快照，支持问题复现与离线调试。

    • 系统监控与告警（Monitoring & Alerting）
      跟踪性能、成本与异常指标，及时发现并处理系统问题。

    Step 7：MVP与持续迭代

    • 核心流程优先落地（MVP Workflow First）
      优先实现单一高频场景，验证系统闭环与可行性。

    • 端到端评估体系（E2E Evaluation）
      构建覆盖正常与异常场景的测试集，评估整体任务成功率与稳定性。

    • 基于日志的持续优化（Iteration via Feedback Loop）
      基于真实运行数据持续优化prompt、流程与系统设计，逐步扩展能力边界。
