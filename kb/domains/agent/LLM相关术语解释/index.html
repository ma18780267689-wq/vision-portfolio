    LLM相关术语解释

    Token

    token定义

    在大模型里，token 是模型处理文本时使用的最小离散单位。 它不等同于“一个字”，也不等同于“一个单词”。一个 token 可能是：

    • 一个汉字
    • 一个词
    • 一个词的一部分
    • 一个标点符号
    • 一个空格或换行的一部分
    • 一段常见字符串

    大模型并不是直接“理解整句文字”，而是先把输入文本切分成一串 token，再对这些 token 进行计算。

    为什么需要 token

    神经网络不能直接处理原始文字，必须先把文本转成可计算的离散符号。 这个离散符号序列，就是 token 序列。

    例如一句话：

    我喜欢学习大模型

    对人来说是 1 句话。 对模型来说，可能会被切成：

    • 我
    • 喜欢
    • 学习
    • 大
    • 模型

    也可能是别的切法，这取决于具体模型使用的分词器（tokenizer）。

    token 不是固定等于“字”或“词”

    不同语言、不同模型，切分方式不同。

    中文里：有时一个汉字就是一个 token。 但也可能：

    • “人工智能” 被切成多个 token
    • “ChatGPT” 被切成 1 个或多个 token
    • 标点 ， 。 也可能单独算 token

    英文里：一个单词不一定是一个 token。

    例如：

    • cat 可能是 1 个 token
    • playing 可能被切成 play 和 ing
    • unbelievable 可能被切成多个子词

    所以 token 更准确地说是：分词器定义出来的文本片段

    模型为什么关心 token

    因为模型的输入输出、计费、上下文长度，通常都按 token 计算。

    比如常见说法：

    • 上下文窗口 128k tokens
    • 输入 1000 tokens
    • 输出 500 tokens
    • API 按 token 收费

    这里的 token，本质上就是模型实际看到和生成的“内部文本单位”。

    token直观理解

    可以把 token 理解成：

    • 对人类来说：文字是按“字、词、句”理解的
    • 对模型来说：文字先被拆成“token 序列”再处理

    也就是：

    文本 → tokenizer 切分 → token 序列 → 模型计算

    Tokenizer

    tokenizer核心作用

    tokenizer 是一个把原始文本变成 token 序列的编码器，同时也能把 token 序列再还原成文本。

    流程大致是：

    文本 → tokenizer → token ID 序列 → 模型

    例如同一句话：

    我今天学习 Transformer

    不同 tokenizer 可能切成：

    • 我 / 今天 / 学习 / Transformer
    • 我 / 今 / 天 / 学习 / Trans / former
    • 更细的子词或 byte 片段

    所以 tokenizer 主要解决的是两个问题：

    tokenizer把无限可能的文本，映射到一个有限词表：自然语言、新词、拼写错误、代码、表情、缩写都可能无限出现。 tokenizer 不会试图把“所有词”都收入词表，而是把文本拆成可复用的子单元。

    tokenizer目标在“压缩效率”和“泛化能力”之间折中

    如果 token 太大：

    • 词表会爆炸

    • 新词处理差

    如果 token 太小：

    • 一段文本会变得很长

    • 模型处理成本变高

    所以 tokenizer 本质是在做一种工程折中。

    tokenizer 一般包含什么

    1.vocabulary（词表）：这是一个固定有限集合。 里面每个 token 都有一个唯一 ID。

    例如可能有：

    • 常见词
    • 子词片段
    • 标点
    • 空格模式
    • 特殊 token

    比如：

    • <BOS>：开始
    • <EOS>：结束
    • <PAD>：填充
    • <UNK>：未知词（有些现代 tokenizer 几乎不用它）
    • 特殊控制 token

    2.切分规则：即“看到字符串后，按什么规则切”。

    常见思路包括：

    • BPE
    • WordPiece
    • SentencePiece
    • byte-level tokenization

    它们的共同目标都差不多：用有限 token，尽量高效地表示尽量多文本

    3.encode / decode 机制：

    • encode：文本 → token IDs
    • decode：token IDs → 文本

    自回归与 decoder-only

    自回归定义

    定义：自回归（autoregressive）指模型在生成序列时，按从左到右的顺序逐步生成；每一步都基于前面已经出现的 token，预测下一个 token。它对应的概率分解形式是 $$ P(x_1, x_2, ..., x_n)=\prod_{t=1}^{n}P(x_t\mid x_{<t}) $$ 其中 $x_{ 表示第 \(t\) 个 token 之前的所有 token。

    直觉：模型不是一次把整段答案整体“想好再吐出来”，而是“先决定下一个 token，再把它接回上下文，然后继续决定下一个 token”。因此，后面的输出依赖前面已经生成的内容，这就是“自回归”里“回归到已有历史”的含义。

    生成过程：若输入是“今天天气”，模型会先预测下一个 token 可能是“很”，再基于“今天天气很”预测下一个 token 可能是“好”，然后继续向后生成。整个回答、文章补全、代码续写，本质上都可以看成这种逐 token 续写过程。

    成立前提：这里讨论的是主流文本生成模型中的自回归语言建模，不是在说时间序列分析里所有“autoregression”的全部含义；两者概念相关，但具体对象和应用场景不同。

    常见误解：自回归不等于“模型只会机械接词”。为了正确预测下一个 token，模型仍然需要利用前文中的语义、语法、结构、约束条件和局部上下文，因此它背后依然涉及复杂的上下文建模。

    自回归与 decoder-only 的关系

    关系：自回归描述的是“怎么生成”，decoder-only 描述的是“网络怎么搭”。两者经常一起出现，但不是同一个概念。更准确地说，decoder-only Transformer 是一种非常适合做自回归生成的主流架构。

    decoder-only 含义：decoder-only 表示模型主体只由一串 Transformer decoder block 堆叠而成，没有单独的 encoder 模块。它的每一层通常使用因果自注意力（causal self-attention），保证当前位置只能看见当前和过去的 token，不能看未来的 token。

    为什么匹配自回归：因为自回归要求“预测当前位置时不能偷看后文”，而 decoder-only 里的因果掩码正好满足这一点。于是模型在训练和推理时都遵循同一条基本约束：只能根据左侧上下文预测下一个 token。

    聊天场景解释：聊天模型也可以视作条件续写。系统提示、历史对话、用户当前问题会被拼成一段上下文，模型接下来要做的事情仍然是：根据这段前文，连续预测后续 token，直到形成完整回答。因此，聊天并不是一种与续写完全不同的机制，而是续写在对话场景下的实现形式。

    容易混淆的点：“decoder-only” 里的 decoder 是 Transformer 架构术语，不是说模型“只会输出不会理解”。它依然会对前文进行复杂建模，只是这种建模发生在只能看左侧的因果注意力框架里，而不是依赖单独的 encoder 先把输入整体编码完。

    自回归生成的运行过程、优势与局限

    运行步骤：自回归生成通常包括四个循环步骤：读取当前上下文；计算下一个 token 的概率分布；按某种解码策略选出一个 token；把这个 token 拼回上下文并进入下一轮。直到遇到结束标记或达到长度限制，生成过程才停止。

    训练与推理区别：训练时，虽然目标仍然是“预测下一个 token”，但通常可以对整段序列并行计算损失；推理时则更明显是串行的，因为第 \(t+1\) 个 token 必须等第 \(t\) 个 token 先生成出来。这也是大模型生成阶段常显得比训练阶段更慢的关键原因之一。

    优势：这种机制和自然语言续写高度一致，训练目标统一，适合文本生成、对话、代码补全等任务；同时它把复杂任务统一为一个核心问题——“给定前文，下一 token 是什么”。

    局限：自回归生成天然会受到前面输出的影响，一旦前面某一步生成偏了，后面可能顺着这个偏差继续展开；同时它的生成过程有串行依赖，因此延迟较难彻底消除。它还不等于模型具有稳定长期记忆，只表示模型在当前上下文内逐步续写。

    和其他 Transformer 范式的区别：encoder-only 模型更偏理解与表征，通常能同时看左右文；encoder-decoder 更偏“输入到输出”的条件生成，如翻译和摘要；decoder-only 则最适合统一做“给定前文继续生成”的任务。主流通用聊天大模型因此大量采用 decoder-only + 自回归的组合。
